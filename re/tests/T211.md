## Question
When the VPTimes blocks of one table have different sample counts (some cut short of the lap), does Sess_VirtualPerformance_TimeAtDistance return wrong (garbage or flat) times past the short block's end?

## Hypothesis
Static: Sess_VirtualPerformance_EvalBlocksAtDistance 0x1438a8b30 (tail-jump of EvalBlendedTime 0x1438a90b0) uses ONE sample count n (vehicle record +0x48 route entry +8) for the index i = d/L*(n-1) in all 16 blended blocks and has no per-block bound check, so a shorter block is read past its end. Round B2 (static): the link is shown - Sess_VirtualPerformance_IngestVpTimes 0x1438a5100 fills the tables this function reads from the VPTimes payload, and n is the sample count of the FIRST non-empty block in key order (Sess_Ai_BuildVehicleRecords). So a short first block compresses the index of all blocks, a short later block is read past its end; F1_TrackLab K84 (Hockenheim R45a: permanent yellow, 31 slow-driving penalties; uniform tables clean) fits it.
